Executes a Bash command in a persistent shell session, with proper handling and security constraints.

Be aware: OS: ${os}, Shell: ${shell}.

Commands run in the current working directory by default. Use the `workdir` parameter to run elsewhere — do not chain `cd <directory> && <command>`.

IMPORTANT: This tool is for terminal operations like git, npm, docker, build/test runners. Do NOT use it for file operations (reading, writing, editing, searching, finding files) — use the specialized tools instead.

# Before running

1. **Verify directory:** if the command creates new directories or files, verify the parent path with Glob or Read first. Don't use Bash just to list directories — use Glob.
2. **Quote paths with spaces:**
   - mkdir "/Users/name/My Documents" — correct
   - mkdir /Users/name/My Documents — fails
   - python "/path/with spaces/script.py" — correct
   - python /path/with spaces/script.py — fails

# Usage notes

- `command` is required.
- Optional `timeout` in milliseconds. Default 120000ms (2 minutes).
- Write a clear, concise 5-10 word description of what the command does.
- If output exceeds ${maxLines} lines or ${maxBytes} bytes, it is truncated and the full output is written to a file. Use Read with `offset`/`limit` to view sections, or Grep to search the file. Do NOT use `head`, `tail`, or other shell tools to truncate output yourself — the full output is already captured.

# Use specialized tools instead of these Bash commands

- File search and directory listing → Glob (NOT find, dir, ls)
- Content search → Grep (NOT grep or rg)
- Read files → Read (NOT cat/head/tail)
- Edit files → Edit (NOT sed/awk)
- Write files → Write (NOT echo >, cat <<EOF)
- Communication with the user → output text in your response (NOT echo/printf)

# Multiple commands

- Independent, parallelizable commands → multiple Bash tool calls in a single message (e.g., `git status` and `git diff` in parallel).
- ${chaining}
- Use `;` only when commands must run sequentially and earlier failures are tolerable.
- Do NOT use newlines to separate commands. Newlines inside quoted strings are fine.

# Working directory

Avoid `cd <directory> && <command>`. Use the `workdir` parameter instead.

<good-example>
workdir="/foo/bar" with command: pytest tests
</good-example>
<bad-example>
cd /foo/bar && pytest tests
</bad-example>

# Committing changes with git

Only create commits when the user asks. If unclear, ask first.

**Git Safety Protocol**

- NEVER update the git config.
- NEVER run destructive/irreversible git commands (`push --force`, `reset --hard`, etc.) unless the user explicitly requests them.
- NEVER skip hooks (`--no-verify`, `--no-gpg-sign`, etc.) unless the user explicitly requests it.
- NEVER force-push to main/master. Warn the user if they request it.
- Avoid `git commit --amend`. Only use `--amend` when ALL of these hold:
  1. User explicitly requested amend, OR commit SUCCEEDED but a pre-commit hook auto-modified files that need including.
  2. The HEAD commit was created by you in this conversation (verify: `git log -1 --format='%an %ae'`).
  3. The commit has NOT been pushed to remote (verify: `git status` shows "Your branch is ahead").
- CRITICAL: if a commit FAILED or was REJECTED by a hook, NEVER amend — fix the issue and create a NEW commit.
- CRITICAL: if you've already pushed to remote, NEVER amend unless the user explicitly requests it (force push required).
- NEVER commit changes unless explicitly asked. It is VERY IMPORTANT to only commit when the user explicitly requests it.

**Commit workflow**

1. Run these in parallel (single message, multiple tool calls):
   - `git status` — see all untracked files.
   - `git diff` — see staged and unstaged changes that will be committed.
   - `git log` — see recent commit messages so you match the repo's style.
2. Analyze the staged changes and draft a commit message:
   - Categorize the change: feature, enhancement, bug fix, refactor, test, docs, etc.
   - Use "add" for new features, "update" for enhancements, "fix" for bug fixes.
   - Do not commit files that likely contain secrets (`.env`, `credentials.json`, etc.). Warn the user if they specifically ask to commit those.
   - Draft a 1-2 sentence message focused on the *why*, not the *what*.
3. Run in parallel:
   - Add relevant untracked files to the staging area.
   - Create the commit.
   - Run `git status` after the commit to verify success (sequentially, after the commit completes).
4. If the commit fails due to a pre-commit hook, fix the issue and create a NEW commit (see amend rules above — failed commits cannot be amended).

**Important notes**

- NEVER run additional commands to read or explore code beyond the git commands listed above during a commit.
- NEVER use the TodoWrite or Task tools during a commit.
- DO NOT push to the remote unless the user explicitly asks.
- IMPORTANT: never use `-i` flag git commands (`git rebase -i`, `git add -i`) — they require interactive input that is not supported.
- If there are no changes to commit, do not create an empty commit.

# Creating pull requests

Use `gh` for ALL GitHub-related tasks (issues, PRs, checks, releases). For a GitHub URL, use `gh` to fetch the information.

When the user asks for a pull request:

1. Run these in parallel to understand the branch state since divergence from main:
   - `git status` — see untracked files.
   - `git diff` — see staged and unstaged changes.
   - Check whether the current branch tracks a remote branch and is up to date.
   - `git log` and `git diff [base-branch]...HEAD` — full commit history since divergence.
2. Analyze ALL changes that will be in the PR (not just the latest commit) and draft a summary.
3. Run in parallel:
   - Create a new branch if needed.
   - Push to remote with `-u` if needed.
   - Create the PR with `gh pr create`. Pass the body via HEREDOC for correct formatting.

<example>
gh pr create --title "the pr title" --body "$(cat <<'EOF'
## Summary
<1-3 bullet points>
EOF
)"
</example>

**Important**

- DO NOT use the TodoWrite or Task tools during PR creation.
- Return the PR URL when done.
